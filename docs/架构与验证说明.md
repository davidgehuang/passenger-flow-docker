# 容器版架构、指标与验证记录

## 1. 设计基线

容器版从原系统提交 `597ba3584e064fbb75e9a5d276902ff02232dcd4` 的业务代码复制而来，保留 Express/EJS、MySQL 业务表和迁移实验入口。新目录的版本为 0.4.0，原目录独立。运行拓扑：

~~~text
Windows Docker Desktop                         腾讯云实验环境
浏览器 → 127.0.0.1:3030 → app ×1             管理机 → kubectl port-forward → ClusterIP Service
                         ↓ MySQL 8                                        ↓
                   Docker 命名卷                                  TKE app Pod ×2
                                                                         ↓ 私网
                                                                 TencentDB MySQL
TCR 私有镜像仓库 → TKE 镜像拉取；Prometheus → ServiceMonitor → 每个 Pod 的 /metrics
~~~

2026-09-30起，镜像入口统一调用container-preflight。本机显式AUTO_INIT_SCHEMA=true、SEED_DEMO_DATA=true，先校验真实账号、补齐表和幂等示例资料；TKE默认两者false，只检查数据库。TKE 通过独立 Job 首次建表，Deployment 自身不建表、不造数。TKE 示例只有一个 SuperNode；两个 Pod 不提供节点或可用区故障容错。数据库和 TKE 资源需由使用者建立。

## 2. 请求、健康检查与数据路径

容器使用 Node 24，应用监听容器内 `0.0.0.0:3030`。这一监听方式仅在 `NODE_ENV=production`、`CONTAINER_RUNTIME=true` 且配置应用 Basic Auth 时允许。Kubernetes Service 为私有 ClusterIP；网页和 `/metrics` 都要求应用账号。`/live` 无数据库查询，只用于进程存活；`/health` 读取数据库版本并检查八张业务表，供就绪探针使用。数据库失联时 Pod 不就绪，但 `/live` 仍可通过，避免 liveness 因短暂数据库故障重启进程。

普通网页读取仍会执行原系统的 SQL。特别是 Dashboard 聚合、Flow Events 的精确分页计数、Migration Lab 的八表精确计数和空间采样，在百万行或小规格数据库上可能造成明显 CPU 与首屏延迟。容器化不改变这些查询成本，也不自动扩容数据库。上线前需在目标数据库上量测查询耗时、CPU、连接数和索引命中。

普通批量造数按小块事务提交、记录迁移批次；一次请求若中途失败，已提交块不会自动回滚。网页持续负载状态原本仅存在 Node 进程内，两副本会出现不同状态、重复启动及随机命中不同 Pod，因此容器版默认 `ENABLE_CONTINUOUS_WORKLOAD=false`，页面禁用 Start/Stop，接口拒绝启动。单次 Generate/INSERT/UPDATE/DELETE 实验仍可由授权用户执行；请避免双人同时大量操作，并核对批次。若需要持续压测，应另设计受控单实例 Job、停止机制和资源限额，不能直接打开此开关。

## 3. 指标口径与采集

`/metrics` 由 `@prometheus-io/client` 输出 Prometheus 文本，走现有 Basic Auth。ServiceMonitor 使用 Secret 中相同的应用账号，按 Service 的 Pod endpoints 采集，而不是通过负载均衡只采一个 Pod。HTTP 路由标签取 Express 声明的路由模板，未知路径统一标为 `unmatched`，避免用户输入产生无限标签。以下指标仅代表**应用 Pod 观测范围**：

| 指标 | 含义与边界 |
| --- | --- |
| `passenger_http_requests_total` | 每进程收到的请求数，含未认证请求与探针；聚合时按 Pod 求和。 |
| `passenger_http_request_duration_seconds_bucket` | HTTP 整体耗时直方图；慢页面可先按 route 定位，再查 DB 慢 SQL。 |
| `passenger_flow_events_total` | 该进程经 Migration Lab 成功提交的事件行数；重启归零，不含外部 SQL、CLI 和 DTS 写入，不能当作数据库总行数。 |
| `passenger_online_stores`、`passenger_online_devices` | 每个 Pod 每 60 秒读取 ACTIVE 门店与 ONLINE 设备的最近成功样本；两个 Pod 显示相同数据库总体，**不要相加**。 |
| `passenger_business_metrics_up` | 最近一次门店与设备采样是否成功；失败时保留旧值并置 0。 |

示例 PromQL：请求速率 `sum(rate(passenger_http_requests_total[5m]))`；95 分位 HTTP 耗时 `histogram_quantile(0.95, sum by (le, route) (rate(passenger_http_request_duration_seconds_bucket[5m])))`；最新在线设备 `max(passenger_online_devices)`，同时检查 `min(passenger_business_metrics_up)`。正式面板应筛选实际 job、namespace 和业务 Pod 标签，避免混入其他同名应用。腾讯云数据库 CPU、连接数指标名称要在实际托管 Prometheus 数据源中确认。

## 4. 多副本与发布边界

两 Pod 共用 TencentDB，不共享进程内缓存、正在执行的 HTTP 请求或持续负载状态。页面上的数据库容量接口有每进程短缓存，因此两个 Pod 的采样时间可能相差数秒；数据读取仍指向同一个库。应用 Basic Auth 是单组账号，不提供角色分级。管理访问宜经受控内网或 `kubectl port-forward`；公网访问需要另配 HTTPS 和访问控制。

数据库连接池限制为每 Pod 5，两个 Pod 基础上限约 10 条；一次性建表 Job 也会短时创建连接。滚动发布 `maxSurge=1` 时短时可有三个 Pod，应按约 15 条连接留余量。发布前确认数据库最大连接数和其他客户端占用。镜像回滚仅回退应用代码，不能回退数据库 DDL、数据或 DTS 进度。首次建表 Job 仅针对新源库；目标库由 DTS 建表时不得运行。

手动发布工作流仅在 GitHub Actions 的 `workflow_dispatch` 触发，要求专用受信 Linux Runner、受限 kubeconfig、TCR 凭据和预建 Deployment。输入未用过的不可变标签；如标签已存在，工作流中止。CI 的 push/PR 流程仅执行 npm 测试、lint 和镜像构建，不推送或部署。首次云部署仍按使用手册人工核对网络与拉取权限。

## 5. 2026-09-27 历史验证记录（不是本次结果）

本轮在本地新目录完成 `npm test`（27 项通过）、`npm run lint`（通过）、Compose 配置解析和全部 Kubernetes/GitHub Workflow YAML 解析。Docker Hub 的 token 服务从本机连接超时；改从官方公共镜像源取得同一 Node 24 Alpine 基础镜像并缓存为 `node:24-alpine` 后，原 Dockerfile 的镜像构建成功。`docker compose --env-file .env.docker up --build --pull never -d` 实际启动 MySQL 8 和应用；启动日志显示新库自动建成八表、种子完成，初始查询结果为 5 家门店、10 台设备、0 条客流。实际运行 Windows `start-docker-local.bat` 和 `verify-docker-local.bat`，启动和验证均通过；后者确认 MySQL 8.0.36 健康。HTTP 实测 `/live`、`/health`、首页、Migration Lab、带认证的 `/metrics` 均为 200；无凭据的 `/metrics` 为 401。随后在此**隔离演示库**通过网页 API 插入 1 条事件，指标计数变为 1；持续负载 Start 返回 503，符合容器默认禁用策略。容器内 `verify-configured.js` 的 12 个页面/接口及只读事务全部通过；以只读根文件系统加 `/tmp` 临时挂载再测，也成功写入临时报告。没有执行浏览器视觉验收，也没有用大规模数据量进行性能验证。

容器根文件系统在 TKE 模板中设为只读，`/tmp` 挂载临时 `emptyDir`；诊断脚本通过 `REPORTS_DIR` 将报告写入 `/tmp/passenger-flow-reports`。该目录会随 Pod 消失，执行诊断后需立即复制报告到安全存储。旧版 `maintenance on/off` 脚本写入项目根目录的标志文件，在此只读容器内不能使用；改 ConfigMap 的 `MAINTENANCE_MODE` 或 `DB_READ_ONLY` 并滚动发布。不要在多 Pod 内直接运行需要共享持久报告的旧快照流程。

腾讯云资源、TCR 推送与拉取、TKE 超级节点调度、TencentDB 私网和 TLS、ServiceMonitor 抓取、Grafana 看板、双 Pod 滚动发布与回退均未在用户环境执行。模板中的占位符不能直接部署。上线前按部署手册逐项做实机验证，记录命令返回、Pod 事件、数据库 CPU 与页面耗时；不要把模板存在视作云端验收完成。

## 6. 推荐的上线验收顺序

1. 本机网络恢复后构建镜像，启动 Compose，验证 `/live`、`/health`、认证后的首页与 `/metrics`；重启容器后确认命名卷仍保留数据。
2. 在独立 TencentDB 测试库执行一次性建表 Job；核对八表、应用账号权限与 `DB_NAME`，再创建 Deployment。
3. 确认两个 Pod 均 Ready、确实调度到预期 SuperNode、从 TCR 私网拉取镜像且没有反复重启；检查 Service 只在集群内暴露。
4. 通过受控 port-forward 查看首页、门店、设备、客流和迁移页面；测量首屏与数据库 CPU。百万行测试需与既有数据库负载隔离。
5. 确认 Prometheus 显示两个 scrape target，`/metrics` 无凭据返回 401；测试滚动发布和镜像回退，并记录发布期间可用性。

以上步骤均不应对既有 AWS/Rocky 服务或腾讯 DTS 目标库直接运行造数、建表或清理命令。
