# Passenger Flow Docker 与 TKE Phase 1 使用手册

本轮已执行的验证及未验证边界见[首次启动修复与验收报告](首次启动修复与验收报告.md)。

## 1. 范围与前提

此目录是独立容器版；原 passenger-flow-system-codex 不参与镜像构建。目标拓扑是 GitHub → 人工验证过的镜像 → TCR → TKE 命名空间 bh-lab 内两个 Pod → 私网 TencentDB MySQL。一个 SuperNode、一个可用区上的两个 Pod 只提供 Pod 级冗余，不能称为应用跨可用区高可用。数据库多可用区能力由 TencentDB 实例配置决定。

你需要自行准备 Docker、TCR 访问凭证、已连接的 TKE 集群、实际 SuperNode、TencentDB 私网端点和数据库账号。TKE 的 TCR 内网免密拉取组件必须按当前集群版本实测；如果不能使用，配置受限范围的 imagePullSecret。不要从此手册推断云资源已经建立。

变量名称按代码使用 DB_NAME，不使用附件中的 DB_DATABASE；数据库名保留 passenger_flow_codex。现有 schema 使用 utf8mb4_unicode_ci，兼容现有 MariaDB 10.3.39 与 MySQL 8 的表定义，不套用只适合 MySQL 8 的 utf8mb4_0900_ai_ci。

## 2. Windows 11 首次部署、登录与验证

### 2.1 准备与环境选择

安装并启动 Docker Desktop，切换到 Linux containers。需要联网下载锁定的镜像和 npm 依赖；不需要在 Windows 安装 MySQL 或 Node.js。日常入口只依赖 Windows PowerShell 5.1 与 Docker Compose v2。

| 环境 | 启动入口 | 配置文件 | 默认地址 | 数据卷 |
| --- | --- | --- | --- | --- |
| 普通本地 | start-docker-local.bat | .env.docker | http://127.0.0.1:3030 | passenger-flow-docker_mysql_data |
| 独立验收 | start-docker-acceptance.bat | .env.docker.acceptance | http://127.0.0.1:3031 | passenger-flow-docker-acceptance_mysql_data |

已经有旧数据或旧密码不明时，先用独立验收入口。两环境可并存；不删除、不迁移、不修改旧卷中的数据。项目名固定，不因移动目录而静默切换卷。若端口占用，修改所选配置的 APP_HTTP_PORT；不会结束其他程序。容器内部仍为3030，数据库仍为3306，不对宿主机发布数据库端口。

### 2.2 首次配置

双击启动入口，按引导设置 DB_NAME、DB_USER、APP_AUTH_USER。默认数据库 passenger_flow_codex，业务账号 passenger_app，网页账号 local-admin。密码分别输入（不回显）；直接回车使用密码学随机生成的32字符密码。保存前检查名称格式；保存后比对 Compose 实际插值值，保留 #、$、空格、引号及反斜杠。换行、空值不允许；不使用 shell 拼接密码。

已存在的配置文件不会覆盖或重新生成。**实际使用的是 .env.docker 或 .env.docker.acceptance，不是 .env，也不是 .env.docker.example。** 启动入口在其 Docker 子进程内忽略同名 shell 变量，防止它们覆盖选定文件；直接手工运行 docker compose 时仍遵循 Docker 自身的环境变量优先级。

查看独立验收密码：双击 show-docker-acceptance-config.bat。普通环境：show-docker-config.bat。配置只在本机记事本显示，不在日志、报告、镜像或网页接口输出，不要截图发送或上传 Git。手工修改特殊字符密码时应保留引号与转义；不确定时先运行验证，不能仅凭文件内容猜实际密码。

### 2.3 启动成功与网页登录

脚本先构建镜像，启动数据库，使用业务账号通过TCP执行 SELECT 1，再启动APP。统一启动检查补齐八张业务表，本地显式启用示例门店和设备，最后验证 /live、/health、认证后的 /metrics、首页及未登录401。数据库和应用阶段分别最多等待180秒；镜像构建最多600秒，HTTP验证每项最多30秒。成功后才显示数据库名称、用户名和地址；应用启动失败不再被描述成网页密码错误。

| 用途 | 用户名 | 密码配置 | 登录位置 |
| --- | --- | --- | --- |
| 网页 | APP_AUTH_USER | APP_AUTH_PASSWORD | 浏览器登录框 |
| 业务数据库 | DB_USER | DB_PASSWORD | MySQL客户端 |
| 数据库管理员 | root | MYSQL_ROOT_PASSWORD | MySQL客户端，仅本地容器管理 |

APP连接数据库固定使用 DB_HOST=db、DB_PORT=3306，通过Docker服务名解析。报错 user@172.x.x.x 中的IP是客户端来源，不是应填写的数据库地址，不需要抓取IP写回配置。

进入 Docker Desktop 的数据库容器，在终端执行（名称按你配置调整）：

~~~bash
mysql --protocol=TCP -h127.0.0.1 -u passenger_app -p passenger_flow_codex
# 提示时输入 DB_PASSWORD；不要用网页密码。
mysql -u root -p
# 提示时输入 MYSQL_ROOT_PASSWORD。
~~~

初始5家门店、10台设备，客流为0；这不表示登录或建表失败。向独立验收库生成少量客流，在项目 PowerShell 执行：

~~~powershell
docker compose -p passenger-flow-docker-acceptance --env-file .env.docker.acceptance exec app node scripts/generate-test-data.js --rows 30 --days 0
~~~

生成后刷新首页和 Flow Events，重复造数会追加。基础资料扩容沿用 db:base-data；大规模造数、精确计数成本见架构说明，不在首次启动过程中自动执行。

### 2.4 再次运行、停止与诊断

双击 verify-docker-acceptance.bat 或 verify-docker-local.bat。先验证容器配置和真实数据库登录，再验证就绪及网页；脱敏结果在 reports/<项目名>-verify.json。普通环境 root 管理员失败只提示，不否定已通过的业务账号；独立验收要求三类账号全部通过。

停止使用 stop-docker-acceptance.bat 或 stop-docker-local.bat，保留容器、卷和配置。应用有45秒正常退出期限。自动化不暂停示例：

~~~powershell
$env:PASSENGER_NO_PAUSE='1'
.\start-docker-acceptance.bat -GeneratedDefaults
.\verify-docker-acceptance.bat
.\stop-docker-acceptance.bat
~~~

-GeneratedDefaults 仅在配置不存在时使用默认用户名和随机密码，不覆盖已有文件。-NoBuild 可复用当前镜像；源码更新后应正常启动重新构建。

### 2.5 旧卷认证拒绝的处理

MySQL镜像的 MYSQL_USER、MYSQL_PASSWORD、MYSQL_ROOT_PASSWORD 只在空卷初始化时创建账号。改变配置或重建容器不会重设已有账号。数据库健康检查现在使用真实业务登录，错误密码不再显示 Healthy；/live只是进程存活，不能当作登录成功证据。

优先恢复创建旧卷时的配置。若知道旧root密码，可在确认正确容器、库名后，用交互式mysql登录并执行受控账号维护，再同步配置；本轮脚本不自动执行这些管理SQL。示例仅供管理员理解：

~~~sql
ALTER USER 'passenger_app'@'%' IDENTIFIED BY '由管理员替换并正确转义的新密码';
~~~

如果旧root密码也未知，先保留卷，使用独立验收新库验证程序；后续单独制定密码恢复方案。**不要运行 down --volumes，也不要删除Docker Desktop卷来修复认证。** 修改网页账号只需重新启动APP；浏览器可能缓存Basic Auth，建议重新开无痕窗口。

## 3. 手工构建与检查镜像

先在本机或受控 Rocky 构建，再考虑 TCR 和 CI：

~~~bash
docker build --build-arg GIT_COMMIT=local -t passenger-flow-docker:local .
docker image inspect passenger-flow-docker:local
docker compose --env-file .env.docker config --quiet
~~~

Dockerfile 使用固定摘要的 node:24-alpine、npm ci 锁定依赖、非 root node 用户；镜像中生成本地前端资源，不依赖运行时 CDN。构建上下文通过 .dockerignore 排除 .env、.env.docker、node_modules、测试报告、数据库文件和 Git 元数据。不要把任何实际数据库密码传给 docker build。

## 4. TencentDB 与 TCR 的人工准备

在同地域、同 VPC 建立 TencentDB MySQL 实例。按实际可用架构选择 MySQL 8.0 或 8.4，并在独立测试库验证本应用；实例跨可用区高可用配置由你在控制台确认。创建数据库 passenger_flow_codex、业务账号及授权；新库的建表 Job 需要 CREATE 权限。数据库只允许 TKE Pod 网段和经批准的管理机访问，不对公网开放 3306。应用 Pod 数为 2，模板把 DB_CONNECTION_LIMIT 设为每 Pod 5，初始最多约 10 条应用数据库连接；上线前核对实例连接上限与现有业务负载。

在 TCR 企业版创建私有命名空间 passenger-flow 和仓库 passenger-flow-app。先手工推送不可变标签的镜像，用户名和密码交互输入，不写进脚本：

~~~bash
docker login <TCR_REGISTRY> -u <TCR_USERNAME>
docker tag passenger-flow-docker:local <TCR_REGISTRY>/passenger-flow/passenger-flow-app:v1.0.0
docker push <TCR_REGISTRY>/passenger-flow/passenger-flow-app:v1.0.0
~~~

核对 TKE 已能通过内网拉取该私有镜像，再部署应用。具体 TCR 插件能力会受集群版本和实例网络设置影响，不能仅因模板未写 imagePullSecrets 就假定可拉取。

## 5. TKE 配置与首次建表

先在受控工作目录复制模板为 *.local.yaml；这些本地文件已被 Git 忽略。分别替换 DB_HOST、镜像摘要及 Prometheus 实例 ID。TCR标签使用版本号或Git SHA且启用不可变策略；Deployment和Job均填写 image@sha256:实际摘要，不用latest。

~~~bash
cp k8s/01-configmap.template.yaml k8s/01-configmap.local.yaml
cp k8s/02-deployment.template.yaml k8s/02-deployment.local.yaml
cp k8s/05-db-init-job.template.yaml k8s/05-db-init-job.local.yaml
cp k8s/04-servicemonitor.template.yaml k8s/04-servicemonitor.local.yaml
~~~

ConfigMap 只放非秘密信息。实际私网 DB_HOST 属于你的环境，留在 *.local.yaml 即可。新源库先由数据库管理员创建库与账号；不要让两个应用 Pod 同时建表。把四个 Secret 键放在工作目录之外权限 600 的安全文件中，格式如下：

~~~text
DB_USER=实际数据库账号
DB_PASSWORD=实际数据库密码
APP_AUTH_USER=应用登录用户名
APP_AUTH_PASSWORD=应用登录密码
~~~

再执行：

~~~bash
kubectl apply -f k8s/00-namespace.yaml
kubectl apply -f k8s/01-configmap.local.yaml
kubectl -n bh-lab create secret generic passenger-flow-secret --from-env-file=/安全目录/passenger-flow-secrets.env --dry-run=client -o yaml | kubectl apply -f -
~~~

Secret 文件不要加入 Git、不要复制到镜像，也不要在终端打印。APP_AUTH_USER/APP_AUTH_PASSWORD 是网页 Basic Auth，与 DB_USER/DB_PASSWORD 完全不同。

若数据库是全新且目前没有八张业务表，替换 Job 镜像后只运行一次：

~~~bash
JOB=$(kubectl create -f k8s/05-db-init-job.local.yaml -o jsonpath='{.metadata.name}')
kubectl -n bh-lab wait --for=condition=complete job/"$JOB" --timeout=180s
# wait必须成功才能继续；失败时查看日志并停止部署。
kubectl -n bh-lab logs job/"$JOB"
~~~

若这是 DTS 迁移目标端，保持 AUTO_INIT_SCHEMA=false，等待 DTS 建表和迁移，不运行该 Job。若数据库已有完整八表，也跳过 Job。示例资料不由Deployment自动创建。新源端需要5店10设备时，可仅在一次性Job的env中设置SEED_DEMO_DATA=true，由统一preflight在建表后补齐；Deployment保持false。DTS目标端不得设置true。镜像默认AUTO_INIT_SCHEMA=false、SEED_DEMO_DATA=false，APP启动前会真实登录并校验八表。

## 6. 部署与访问

在 SuperNode、TCR 拉取和数据库私网访问都确认后：

~~~bash
kubectl apply -f k8s/02-deployment.local.yaml
kubectl apply -f k8s/03-service.yaml
kubectl -n bh-lab rollout status deployment/passenger-flow --timeout=300s
kubectl -n bh-lab get pods -l app=passenger-flow -o wide
kubectl get nodes -L node.kubernetes.io/instance-type
~~~

两个 Pod 应为 Ready，节点标签应符合 eklet。应用容器监听 0.0.0.0:3030，仅由私有 ClusterIP Service 对内发布 80。/live 只检查进程，不触发数据库；/health 检查数据库及八表，供就绪探针使用。不要把 Service 直接改为公网 LoadBalancer；今后如需公网入口，先设计 HTTPS、访问控制与证书。

管理机上开一个终端：

~~~bash
kubectl -n bh-lab port-forward svc/passenger-flow 8080:80
~~~

另一个终端检查：

~~~bash
curl -fsS http://127.0.0.1:8080/live
curl -fsS http://127.0.0.1:8080/health
curl -u <APP_AUTH_USER> http://127.0.0.1:8080/metrics
~~~

不带应用账号访问 /metrics 应返回 401。不要执行 printenv 或 env | grep DB_，因为它会同时打印 DB_PASSWORD。

## 7. Prometheus、Grafana 与 CI

先核对 ServiceMonitor CRD 和实际 Prometheus ID，再应用 k8s/04-servicemonitor.local.yaml：

~~~bash
kubectl get crd servicemonitors.monitoring.coreos.com
kubectl apply -f k8s/04-servicemonitor.local.yaml
kubectl -n bh-lab get servicemonitor passenger-flow
~~~

ServiceMonitor 使用同一个应用 Secret 的 Basic Auth 键抓取 /metrics，预期每个 Pod 各有一个采集目标。Grafana 首先验证 passenger_http_requests_total、passenger_http_request_duration_seconds_bucket、passenger_flow_events_total、passenger_online_stores、passenger_online_devices 和 passenger_business_metrics_up。数据库指标从腾讯云监控集成核对实际名称后再做面板，不预填未经验证的 PromQL。详细指标语义见架构说明。

GitHub 新建一个空仓库 passenger-flow-docker，不要勾选初始化 README。此目录独立初始化并由你自行提交：

~~~bash
git init -b main
git add .
git status
git commit -m "Add containerized passenger flow lab"
git remote add origin <你的新仓库HTTPS或SSH地址>
git push -u origin main
~~~

推送 main 只触发 CI 的 npm 测试、检查和镜像构建，不会自动推送 TCR 或改 TKE。首次手工 Build → Push → Deployment 成功后，才在 GitHub 配置专用 Linux Runner 标签 tke-lab、仓库变量 TCR_REGISTRY、TCR_IMMUTABLE_TAGS_CONFIRMED=true（确认TCR已开启标签不可变后设置）、Secret TCR_USERNAME/TCR_PASSWORD 和受限 kubeconfig，然后人工触发 Manual TCR and TKE Release。工作流仅在明确manifest不存在时允许使用新标签，网络和认证错误会停止；同环境发布串行、Node24固定、部署使用推送后的摘要、临时登录目录始终清理。仓库端仍须启用标签不可变，以避免其他发布者覆盖。不要把堡垒机长期当作通用 CI Runner；正式使用需独立主机和最小权限。

## 8. 回退与边界

只回退应用镜像：

~~~bash
kubectl -n bh-lab rollout history deployment/passenger-flow
kubectl -n bh-lab rollout undo deployment/passenger-flow
kubectl -n bh-lab rollout status deployment/passenger-flow
~~~

镜像回退不会回滚数据库结构、数据、DTS 进度或外部负载任务；数据库切换必须沿用原系统的停写、快照和对账流程。ConfigMap/Secret 更新后需显式重启或滚动发布，现有 Pod 不会自动读取新环境变量。TKE 容器根目录只读；诊断报告临时写到 `/tmp/passenger-flow-reports`，执行后及时导出，Pod 重建后会丢失。维护模式通过 ConfigMap 的 MAINTENANCE_MODE 或 DB_READ_ONLY 开启并滚动发布，不使用会写项目根目录的旧 `maintenance on/off` 脚本。数据库 TLS 初始模板为 false，仅用于私网实验；拿到 TencentDB CA 后设置 DB_SSL=true、DB_SSL_CA 并把证书以 Secret 文件挂载，保留证书校验。

腾讯云参考：[超级节点调度](https://cloud.tencent.com/document/product/457/54754)、[TCR 与 TKE 集成](https://cloud.tencent.com/document/product/1141/48186)、[Prometheus 抓取配置](https://cloud.tencent.com/document/product/248/87378)。具体计费、实例规格、插件支持与控制台路径以部署当天实际配置为准。

## 9. 开发者复测（仅独立验收项目）

日常双击入口不需要Node；复测源码需要Node24、Windows Edge及Docker Desktop。浏览器自动化依赖作为devDependency锁定，不进入生产镜像。步骤：

~~~powershell
npm ci --cache .npm-cache
npm test
npm run lint
$env:PASSENGER_NO_PAUSE='1'
.\start-docker-acceptance.bat -GeneratedDefaults
npm run test:docker-local
npm run test:docker-browser
.\verify-docker-acceptance.bat
~~~

集成测试只面向固定的独立验收项目，每次追加30条客流并测试重启保留。故障测试创建第三个带时间戳的独立项目，证明修改环境密码不会修改持久账号；随后停止其容器、保留测试卷。还会临时改动并恢复验收配置以验证实际BAT的失败行为，不要在测试期间手工编辑验收配置。不会修改普通 .env.docker 或旧卷。自动浏览器使用Edge headless，检查七个页面、六张图表和移动视口；截图与脱敏报告放在reports/，不进入Git或镜像。故障测试前会将验收配置备份到reports/.env.acceptance-before-fault-test-<时间戳>（私密文件，被Git和镜像排除）。若测试进程被强制终止且验收认证失败，先确认处于故障测试阶段，将对应备份恢复为.env.docker.acceptance，再运行验收启动入口，保留数据卷。

独立目录尚未初始化Git时，git diff不会显示未跟踪文件的内容。按第7节自行git init并提交；已建仓库的使用git diff --stat和git diff检查差异。本轮不会替你提交或推送。
